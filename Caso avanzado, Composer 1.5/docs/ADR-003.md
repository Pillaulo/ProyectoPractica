# ADR-003: SQLite para Desarrollo con Ruta a PostgreSQL

**Estado:** Aceptado
**Fecha:** Marzo 2026
**Contexto del decisor:** Arquitecto de Software Senior

---

## Contexto

El PRD requiere persistencia obligatoria con base de datos. Necesitamos elegir el motor de base de datos para el MVP.

### Opciones

1. **PostgreSQL desde el inicio**: motor robusto, estándar de producción.
2. **SQLite para desarrollo**: archivo local, cero configuración.
3. **MongoDB**: base documental, esquema flexible.
4. **SQLite ahora, PostgreSQL después**: SQLite en desarrollo, con SQLAlchemy como abstracción para migrar luego.

## Decisión

Usamos **SQLite para desarrollo** con SQLAlchemy como ORM, diseñado para una migración transparente a PostgreSQL en producción.

## Justificación

| Criterio | PostgreSQL | SQLite | MongoDB |
|----------|-----------|--------|---------|
| Configuración inicial | Requiere instalar y configurar servidor | Cero — archivo local | Requiere instalar servidor |
| Modelo de datos | Relacional (perfecto para nuestras entidades) | Relacional | Documental (no natural para relaciones Profile→Story→Fragment) |
| Complejidad de setup para desarrollo | Alta | Nula | Media |
| Compatibilidad con SQLAlchemy | Total | Total | Requiere motor distinto (MongoEngine) |
| Migración futura | — | Solo cambiar `DATABASE_URL` | Reescribir repositorios |
| Adecuación al MVP | Sobredimensionado | Perfecto | Modelo no ideal |

### Razones clave

- **Cero infraestructura**: SQLite no necesita servidor, instalación ni docker. Ideal para desarrollo local y evaluación del experimento.
- **Mismo ORM**: gracias a SQLAlchemy, el código de los repositorios es idéntico para SQLite y PostgreSQL. Solo cambia la cadena de conexión.
- **Arquitectura hexagonal lo habilita**: como los repositorios implementan puertos (interfaces), la base de datos es un detalle de implementación que se puede cambiar sin afectar dominio ni aplicación.
- **Nuestros datos son relacionales**: Profile → Story → Fragment es un modelo relacional natural. MongoDB no aporta ventaja y complicaría las consultas.

## Consecuencias

**Positivas:**
- Desarrollo inmediato sin instalar nada.
- Base de datos es un solo archivo `.db` que se puede borrar y recrear fácilmente.
- Migración a PostgreSQL = cambiar una variable de entorno (`DATABASE_URL`).
- SQLAlchemy maneja las diferencias dialectales automáticamente.

**Negativas:**
- SQLite no soporta concurrencia de escritura (un solo escritor a la vez). Para un MVP con un usuario, esto es irrelevante.
- Algunas features de PostgreSQL (JSONB, arrays nativos, full-text search) no están disponibles en SQLite. No las necesitamos en v1.

## Plan de migración

1. Cambiar `DATABASE_URL` de `sqlite:///./cuentomagico.db` a `postgresql://user:pass@host/db`.
2. Ejecutar la creación de tablas (SQLAlchemy `create_all` o Alembic migrations).
3. Sin cambios en código de dominio, aplicación ni repositorios.
