# ADR-006: Diseño de API REST

**Estado:** Aceptado  
**Fecha:** Marzo 2025  
**Decisores:** Arquitecto, Equipo técnico

---

## Contexto

El frontend consumirá el backend vía HTTP. Se debe definir un contrato claro, predecible y alineado con REST.

---

## Decisión

API REST con los siguientes principios:

- **Recursos:** `/profiles`, `/profiles/:id`, `/profiles/:id/stories`, `/stories/:id`
- **Verbos HTTP:** GET (lectura), POST (crear), DELETE (eliminar)
- **Códigos:** 200 OK, 201 Created, 404 Not Found, 400 Bad Request, 500 Internal Server Error
- **Formato:** JSON en request y response
- **Sin versionado en URL** en v1 (ej. no `/v1/profiles`); posible header `Accept-Version` si se necesita después
- **Health check:** `GET /health` → `{ "status": "ok" }`

---

## Alternativas consideradas

| Alternativa | Pros | Contras | Descartada por |
|-------------|------|---------|----------------|
| **GraphQL** | Flexibilidad en queries; un endpoint | Más complejidad; overfetch no es problema actual | Sobredimensionado para v1 |
| **gRPC** | Alto rendimiento; contratos fuertes | No navegable desde browser; más setup | REST suficiente para web |
| **REST con HATEOAS** | Hipermedia; descubribilidad | Complejidad; poco adoptado en SPAs | No aporta valor inmediato |
| **REST simple (elegida)** | Estándar; fácil de consumir; tools (Postman, curl) | Menos expresivo que GraphQL | Adecuado para alcance v1 |
| **Versionado en URL** | Claro para evolución | Más ruido en v1 | Se evita hasta tener breaking changes |

---

## Consecuencias

### Positivas

- Contrato fácil de documentar (OpenAPI/Swagger opcional)
- Frontend puede usar `fetch` o axios sin complejidad
- Compatible con caché HTTP estándar (GET)

### Negativas

- Posible sobrecarga de peticiones (N+1) si no se diseña bien; mitigar con respuestas que incluyan datos necesarios (ej. story con fragments en un GET)

### Trade-off aceptado

REST sencillo y predecible; evolución mediante nuevos recursos o query params en lugar de versionado explícito en v1.
