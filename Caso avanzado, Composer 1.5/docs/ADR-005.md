# ADR-005: Construcción de Prompts en Capa de Infraestructura

**Estado:** Aceptado
**Fecha:** Marzo 2026
**Contexto del decisor:** Arquitecto de Software Senior

---

## Contexto

Para generar cuentos personalizados, el sistema debe construir un prompt que incluya el nombre del niño, su nivel lector, el tema elegido y las instrucciones de estilo/longitud. La pregunta es: ¿dónde vive la lógica de construcción de prompts?

### Opciones

1. **En el dominio**: el servicio de dominio construye el prompt como parte de las reglas de negocio.
2. **En el caso de uso**: el caso de uso arma el prompt antes de invocar el puerto del generador.
3. **En el adaptador LLM (infraestructura)**: el adaptador recibe parámetros de negocio y construye internamente el prompt específico para su proveedor.

## Decisión

La construcción de prompts vive en la **capa de infraestructura**, dentro del adaptador LLM, con un módulo auxiliar `prompt_builder.py`.

## Justificación

| Criterio | En dominio | En caso de uso | En infraestructura |
|----------|-----------|---------------|-------------------|
| Pureza del dominio | Violada (el dominio conocería detalles de cómo hablar con un LLM) | Parcialmente violada | Respetada |
| Especificidad del proveedor | El prompt podría no ser óptimo para todos los LLMs | Genérico, pero rígido | Optimizado para cada proveedor |
| Intercambiabilidad | Un cambio de LLM requiere cambiar el dominio | Un cambio de LLM requiere cambiar el caso de uso | Solo cambia el adaptador |
| Testabilidad del prompt | Compleja (dominio no debería saber de prompts) | Media | Alta (unit test del builder) |

### Razones clave

- **Un prompt es un detalle de implementación del proveedor**, no una regla de negocio. El dominio sabe que necesita "generar un cuento dados un nombre, nivel y tema", no cómo pedírselo a GPT-4.
- **Cada LLM tiene sus propias mejores prácticas de prompting**. Un prompt óptimo para GPT-4 puede diferir del ideal para Claude o Gemini. Si el prompt estuviera en dominio o aplicación, un cambio de proveedor requeriría modificar esas capas.
- **El puerto `StoryGeneratorPort` define un contrato limpio**: `generate(prompt: str) → str`. Pero internamente el caso de uso no construye el prompt de texto; en su lugar, el caso de uso pasa parámetros de negocio (nombre, nivel, tema) al adaptador, y este construye el prompt.

### Refinamiento del puerto

Para mantener la coherencia, el puerto se ajusta para recibir parámetros de dominio en vez de un string de prompt crudo:

```python
class StoryGeneratorPort(Protocol):
    def generate(
        self,
        child_name: str,
        reading_level: ReadingLevel,
        theme: Theme,
    ) -> str: ...
```

De esta forma:
- El caso de uso pasa datos de dominio.
- El adaptador traduce esos datos a un prompt específico para su proveedor.
- El dominio nunca conoce la palabra "prompt".

## Consecuencias

**Positivas:**
- Dominio y aplicación libres de detalles de prompting.
- Cada adaptador puede optimizar su prompt para su proveedor específico.
- Cambiar de proveedor LLM no toca dominio ni aplicación.
- `prompt_builder.py` es un módulo puro y testeable de forma aislada.

**Negativas:**
- Si se quiere dar al usuario control fino sobre el prompt (ej: "instrucciones personalizadas"), habría que propagar esa configuración desde dominio hasta el adaptador. Para v1 esto está fuera de alcance.
- El puerto ya no recibe un `str` genérico, sino parámetros de dominio, lo cual es ligeramente más acoplado. Aceptamos este trade-off porque refleja mejor la intención: "genera un cuento para este perfil", no "envía este texto".

## Estructura resultante

```
infrastructure/
└── llm/
    ├── openai_generator.py    # Implementa StoryGeneratorPort
    └── prompt_builder.py      # Construye prompt a partir de parámetros de dominio
```

El `prompt_builder` es una función pura:

```python

```

El `openai_generator` la invoca internamente:
