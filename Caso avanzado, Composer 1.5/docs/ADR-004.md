# ADR-004: Inyección Manual de Dependencias sin Framework DI

**Estado:** Aceptado
**Fecha:** Marzo 2026
**Contexto del decisor:** Arquitecto de Software Senior

---

## Contexto

La arquitectura hexagonal requiere que los casos de uso reciban sus dependencias (repositorios, generadores) por constructor, no que las instancien internamente. Necesitamos decidir cómo realizar esa inyección.

### Opciones

1. **Framework DI** (ej: `dependency-injector`, `inject`, `python-inject`): configuración declarativa, resolución automática.
2. **Sistema DI de FastAPI** (`Depends`): integrado en el framework, pero acoplado a FastAPI.
3. **Inyección manual** (composition root): instanciación explícita en `main.py`, paso por constructor.

## Decisión

Usamos **inyección manual** con un composition root en `main.py`.

## Justificación

| Criterio | Framework DI | FastAPI Depends | Inyección manual |
|----------|-------------|-----------------|-----------------|
| Dependencia externa | Sí (librería adicional) | No (viene con FastAPI) | No |
| Acoplamiento al framework | Al framework DI | A FastAPI | Ninguno |
| Transparencia | Mágica (resolución automática) | Semi-transparente | Totalmente explícita |
| Complejidad de configuración | Media-Alta | Baja | Nula |
| Testabilidad | Buena | Buena | Excelente (constructor puro) |
| Adecuación al tamaño del proyecto | Sobredimensionado | Aceptable | Perfecta |

### Razones clave

- **Explícita y trazable**: al leer `main.py` se ve exactamente qué recibe cada caso de uso. Sin magia, sin decoradores, sin contenedores.
- **Sin acoplamiento**: si se cambia FastAPI por otro framework, la composición se reescribe trivialmente. Con `Depends` de FastAPI, los casos de uso quedarían acoplados al framework.
- **Pocos componentes**: tenemos ~8 casos de uso y ~3 adaptadores. Un framework DI brilla con decenas de servicios; aquí es overhead.
- **Tests simples**: en tests, se instancian los casos de uso pasando fakes/mocks directamente al constructor. Sin configurar contenedores.

## Consecuencias

**Positivas:**
- Cero dependencias adicionales.
- Composición legible en un solo archivo.
- Tests unitarios que instancian casos de uso con fakes en una línea.
- Dominio y aplicación completamente desacoplados de cualquier mecanismo DI.

**Negativas:**
- Si el proyecto creciera a decenas de servicios, la composición manual se volvería verbosa. En ese punto se evaluaría migrar a un framework DI.
- No hay auto-descubrimiento de dependencias (no es un problema real para este tamaño).

## Patrón de composición

```python
# main.py — Composition Root (pseudocódigo)

# Infraestructura
profile_repo = SqlReaderProfileRepository(session)
story_repo = SqlStoryRepository(session)
generator = OpenAIStoryGenerator(api_key)

# Dominio
fragmenter = FragmentationService()

# Aplicación
create_profile = CreateReaderProfileUseCase(profile_repo)
generate_story = GenerateStoryUseCase(story_repo, profile_repo, generator, fragmenter)

# HTTP (el único lugar que conoce todo)
app.include_router(profile_router(create_profile, ...))
app.include_router(story_router(generate_story, ...))
```
