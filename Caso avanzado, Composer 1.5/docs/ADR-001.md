# ADR-001: Arquitectura Hexagonal sobre MVC Tradicional

**Estado:** Aceptado
**Fecha:** Marzo 2026
**Contexto del decisor:** Arquitecto de Software Senior

---

## Contexto

Necesitamos definir la arquitectura del backend de CuentoMágico. Las opciones principales son:

1. **MVC tradicional** (Model-View-Controller) — estructura sencilla y familiar.
2. **Arquitectura hexagonal** (Ports & Adapters) — núcleo de dominio aislado con interfaces explícitas.
3. **Clean Architecture** — variante más formal con múltiples anillos.

El proyecto tiene dependencias externas significativas (LLM, base de datos) que podrían cambiar en el futuro, y un requisito explícito de que el dominio no dependa de infraestructura.

## Decisión

Adoptamos **arquitectura hexagonal** con tres capas: dominio, aplicación e infraestructura.

## Justificación

| Criterio | MVC | Hexagonal | Clean Architecture |
|----------|-----|-----------|-------------------|
| Aislamiento de dominio | Bajo (modelo acoplado a ORM) | Alto (dominio puro) | Muy alto |
| Complejidad | Baja | Media | Alta |
| Testabilidad | Media (requiere mocks de DB) | Alta (puertos fáciles de mockear) | Alta |
| Intercambiabilidad de adaptadores | Difícil | Fácil | Fácil |
| Curva de aprendizaje | Baja | Media | Alta |
| Adecuación al tamaño del proyecto | Sobredimensionado para lo simple | Justo | Sobredimensionado |

### Por qué no MVC

En MVC los modelos suelen estar acoplados al ORM (SQLAlchemy models = entidades de negocio), lo que viola el requisito de dominio independiente. Cambiar de proveedor LLM o base de datos requeriría modificar lógica de negocio.

### Por qué no Clean Architecture completa

Clean Architecture añade capas adicionales (entities, use cases, interface adapters, frameworks) que para un MVP de esta escala introducen burocracia sin beneficio proporcional.

### Por qué hexagonal

- El dominio queda completamente aislado: entidades y value objects son clases Python puras.
- Los puertos (Protocols) permiten testear casos de uso con implementaciones fake sin necesidad de base de datos ni API externa.
- Si en el futuro se cambia de OpenAI a Anthropic, solo se crea un nuevo adaptador.
- La complejidad es manejable para un equipo pequeño.

## Consecuencias

**Positivas:**
- Dominio libre de imports de frameworks.
- Adaptadores intercambiables sin tocar lógica de negocio.
- Casos de uso testeables de forma unitaria.
- Estructura de carpetas que comunica la intención arquitectónica.

**Negativas:**
- Más archivos y carpetas que MVC.
- Mapeo explícito entre modelos ORM y entidades de dominio (boilerplate de conversión).
- Requiere disciplina para no "atajar" importando infraestructura en dominio.

## Riesgos

- **Erosión arquitectónica**: con el tiempo, desarrolladores podrían importar SQLAlchemy en el dominio por comodidad. Mitigación: revisiones de código y regla de linter que detecte imports prohibidos en `domain/`.
